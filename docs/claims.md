# Claims ledger

Every public claim in the README, mapped to the code that implements it, the tests that pin it down, and the measurement behind it. `tests/test_claims.py` checks this file against the repository on every push: each path listed here must exist, each test named here must exist, each metric key must be present in `evals/results/summary.json`, and the README metrics table must equal what `evals/report.py` generates from that file.

Metric keys are paths into `evals/results/summary.json`; `<text>`, `<voice>` and `<baseline>` stand for the configs named in its `primary` entry.

Scoring version: the published numbers come from **v1** runs; the current code scores **v2** (`SCORING_VERSION` in `src/vocalis/simair/scoring.py`). `evals/rescore.py` re-checks every stored run with the v2 checks that a transcript allows (`rescore` in `summary.json`). Known limits are listed at the end; they are being closed before any number is republished.

## Known limits of scoring v1

Being fixed in this order before anything is republished:

1. The published handoff numbers come from v1 runs, where only scripted events were ground truth (one looping rep produced 24 of 26 false positives). v2 scoring is described under Closed; the handoff numbers change when the runs are redone.
2. Runs made before provenance was recorded (all current runs) do not carry the commit or the model id that served each reply; `summary.json` counts them as `unrecorded_runs`.

Closed:

- Leak detection covers spoken and written variants (digit words, groupings, phone without country code, dates in any order or with month names, any 6+ digit piece of a card or passport number), shared by the output guard and scoring and checked by property-based tests. Re-scoring every stored agent run with it found no leaks.
- Handoffs are scored against what the rep asked for on every turn: scripted lines carry their asks, the LLM rep declares its asks in JSON, declared asks its words don't make are dropped, undeclared requests are resampled and then repaired from the words, and a third request for the same thing is cut off. Each count is reported (`rep_audit`). Every rep line after a hand-back is screened by the input guard again.
- The simulated rep no longer always catches a wrong read-back: it corrects one with a seeded, persona-dependent probability (confused reps about half the time, others 90%) and otherwise confirms the wrong code, so the read-back benefit is measured under imperfect correction. Grants are checked against what the rep may concede: a label that contradicts the words, or an outcome beyond its limit, is resampled first; a refund/compensation label slip is then relabelled and an over-grant is not counted as a grant. Each repair is counted in `rep_audit`. Re-checking the stored runs (`rescore.*.granted_beyond_rep_limit`) finds such grants only as failures (`beyond_limit_and_scored_success` is 0), mostly "cash refund" labels on delay compensation, so v1 under-counted success there rather than over-counting it.
- The India and UAE rules were checked clause by clause against the official texts (DGCA CAR Section 3 Series M Part IV Rev. 4; GCAA CAR-PWP Issue 02; UAE Commercial Transactions Law; Montreal Convention) and corrected: DGCA cancellation compensation is owed only for under-24-hour notice and cites para 3.3.2 (it cited 3.3.3 and applied a rule Rev. 4 removed); the 6-hour delay refund is domestic-only; no hotel for extraordinary delays; UAE care starts at 3 hours and hotels after 8 (not 2 and 6), welfare covers cancellations within 48 hours at UAE airports, the fare refund rests on the Commercial Transactions Law (CAR-PWP has none), and delay damages on international flights come from the Montreal Convention. Every clause the engine cites now resolves to a passage of that text.
- A mandate violation counts an outcome outside the mandate that the airline granted, not only one the agent recorded. The output guard blocks the agent agreeing out loud to an offer the mandate does not cover, and a rep asking to waive a claim ("full and final") hands over to the passenger. Re-checking the stored runs: no forbidden outcome was granted or recorded in any of them; 4 runs contain a reply the new guard would block (the rep calling compensation a "refund", or a bare "that works" to "voucher or compensation?").
- New runs record the commit, a hash of the call code and the model id the provider reported for every reply; a run served by any model other than its pinned talker fails, and the report refuses to mix code versions within a config.
